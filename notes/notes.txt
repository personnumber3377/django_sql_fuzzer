
The fuzzer uses atheris which is a coverage guided fuzzer developed by google. It essentially does for python what AFL and libFuzzer do for C and C++.

The fuzzer works by taking one byte from the input and then using that as an index into a list of "target functions" which each do something interesting with the django sql operations. Then after the operation is done, the result is checked for interesting exceptions like a database error or something signifying broken SQL. Then the resulting query is passed to a function called `check_sql_semantics` which, as the name implies, checks the resulting query (which is returned as a string from the target function) for suspicious patterns. This checker is still quite broken and does a lot of false positive results and should not be trusted yet.

SQL-Injection: The fuzzer also found a potential SQL injection, but I am quite sure that this is a false positive. Still decided to mention in case it is not and I am misunderstanding something. It is in a file called sqli.txt and you can run it the same way `TESTING=1 python3 main.py sqli.txt` . This seems to stem from the fact that when using concatenation in sql queries, the checker function called `check_sql_semantics` is too eager and reports the `SELECT `app_author`.`id`, `app_author`.`name`, CONCAT_WS('',  OR 1=1/*otas_book --, test) AS `c` FROM `app_author`` query as sql injection because it seems to break context, however, the value is passed in as an argument which can be seen from `qs.query.sql_with_params()`, but from the string representation of the query it seems to break context even though it doesn't in reality.
